# Changelog

Purpose: describe changes in the two packages a module installs.
Read this when: choosing or upgrading a package version.
Related: [README](README.md), [new module](docs/guides/new-module.md), [UI package](packages/ui/README.md), [BFF package](packages/bff/README.md).

## Unreleased

- `@eneo-ai/module-kit`: a sign-in that fails in the sign-in dialog's login window says so there and stays (`LoginWindowFailed`: close the window and try again from the page). It tells the page nothing and offers no sign-in of its own, and the page keeps its cover or its warning; before, the window showed the module's sign-in screen, and a sign-in from there ended in the window. The dialog marks the window as it opens it: the mark is in the page's `sessionStorage` for the moment of the call, and the browser gives a window opened with an opener a copy, which outlasts a page on the way that sets `Cross-Origin-Opener-Policy`; where the window gets no copy, a failure meets the module's ordinary handling at `/` ([K20](docs/decisions/k20-the-login-window-knows-itself.md)). Every press opens a new window without a name and closes the one the dialog opened before, when it can still reach it. `isLoginWindow()` says whether a page is in that window; the kit's `SignInScreen` shows the failure view there, and in that window `RequireSession` shows only the failure view, whatever the path: no status read, no sign-in, no dialog, no page. `SignedInAgain` takes a refusal in its address (`fel=`, the last one it recognises) over its `refusal` prop. The window's pages are drawn on the theme's surface: without it the accessibility check failed the failure view's contrast in dark mode. Breaking, when upgrading: route `SignedInAgain` on a page of its own outside `RequireSession`. In the login window the gate shows only the failure view, so a completed sign-in on a page inside it would tell the page nothing. A module that had it inside the gate on a path of its own moves that route out and keeps the path. A module whose guarded `/` was also the window's page gives the window a path of its own outside the gate (the default `/inloggad`), sets `signedInAgainPath` to it, and leaves `/` as it is: `SignedInAgain` moved to an unguarded `/` would take the place of the sign-in. `auth_error` on `/` is the backend's; a module that keeps the window's page on `/` and uses a query key of that name there renames it. Then the page at `/`, where a failure in the login window lands: if it is a page of the module's own outside the gate, a public home page or a sign-in screen, it must show `LoginWindowFailed` while `isLoginWindow()` is true (add the check).
- `eneo-module-bff` holds the home path to the rule a login's `next` follows: `create_app` refuses to start with a `home_path` that does not start with `/`, starts with `//`, or holds a backslash, as it already did for a control character or more than 256 bytes of UTF-8, and says which. A home path that cannot be written as UTF-8 (a lone surrogate) now stops the start with the same kind of message instead of a `UnicodeEncodeError`. The home path is read once, at start: a change to the `Settings` object after `create_app` reaches no redirect. The callback checks a login's stored destination by the same rule when it reads it. Breaking, when upgrading: a `home_path` that started before and breaks one of these rules (such as `//host`, `/a\b`, `flows` or an empty one) now stops `create_app`; give it a path of the module, such as `/flows`.
- The template's desktop Firefox project (`firefox`) now selects `login-window.spec.ts` too, as the Chromium and WebKit projects do.
- The template's stub Eneo has a control `/__stub/module-login?ticket=normal|refused&opener_policy=none|same-origin`: the next logins' tickets are refused by the exchange (the callback ends as `exchange_failed`), and Eneo's login sends the browser back through a page with `Cross-Origin-Opener-Policy: same-origin`.

- `eneo-module-bff` ends a session when Eneo confirms that the user's login is over (a changed password, "log out everywhere"): Eneo refuses the token with 401 `authentication_error` and its session route refuses the same token. The browser gets the 401 of an ended session (`X-Auth-Required: session`) and its page asks for a new login, instead of showing Eneo's refusal. Anything else Eneo answers goes on unchanged and the session stays. The proxy, `forward_upload` and the minting in `stream_signed` apply it; a module's own call to Eneo gets it with the new `raise_if_session_ended(request, answer)`. A test double for Eneo that answers 401 `authentication_error` now also gets a `GET /api/v1/module-auth/{module_key}/session/` with the same token: answer it 401 `authentication_error` to end the session, or 200 with the session's identity to keep it.
- `eneo-module-bff` gives a person `LOGIN_TIMEOUT_MINUTES` (30 by default, was a fixed five minutes) to sign in at Eneo, so that someone who must first sign in to Eneo itself no longer comes back to `invalid_state`.
- `eneo-module-bff` gives each login a state cookie of its own on `/api/auth`, so a second login (another tab, the session cover's sign-in) no longer ends the first; a new login deletes the oldest past five waiting (a cleanup, not a limit: two starts at once leave six until the next start, and simultaneous starts are not bounded), and a `next` whose signed state would pass 1024 bytes is the home path, so six waiting cookies, which go with every `/api/auth` request, stay under a proxy's 8 KB header limit. A `home_path` over 256 bytes of UTF-8, or with a control character, stops `create_app` with a message that names it. When upgrading: the old `eneo_module_login_state` cookie on `/api/auth/callback` is ignored, so a login in flight at the upgrade fails once as `invalid_state` and the next one works.
- The template's stub Eneo refuses with Eneo's own bodies (`authentication_error`, `invalid_api_key`), asks for both credentials on every `/api/v1/` route, and has two more controls: `/__stub/resources?answer=refused` (Eneo's routes refuse a token its session route still takes) and `GET /__stub/calls` (how often the session route and the refresh were asked). After `/__stub/end-session` the module's session ends at its next call to Eneo.
- `@eneo-ai/module-kit` needs `@astryxdesign/core` 0.7.12, and the template pins Astryx's core and CLI at 0.7.12. Astryx no longer makes a warning or an error banner an alert by itself: the offline notice, the sign-in and session problems, a version that cannot be read and the template's flow list that cannot be shown say `role="alert"` themselves, which Astryx puts on the title and description. The providers give Swedish words for design-system strings that Astryx's Swedish catalog lacks: a scrolling region's name, a clear button, a failed copy and a date that does not exist. `LoadingShell`'s spinner, which Astryx would now read out, is silent: the page is said once it has its content, and the word "Laddar" stays for a screen reader to find. `base.css` carries Astryx's layer position rules, which Astryx 0.7.12 would write into a `<style>` that the strict `style-src 'self'` refuses, and `ModuleProviders` renders the element Astryx looks for first, so a menu or popover opens with no policy violation.
- `scripts/new-module.mjs` makes a module from the template with the packages of a checkout in one command, and a module's `stub-eneo/dev.mjs` starts the stub Eneo and the module together; `--check` signs in and stops. Both run on macOS, Linux and Windows, and the kit's CI runs them on each.
- The UI package's build and the unit-test scripts of the package and the template run on Windows.

## 0.1.0 — 2026-11-08

- `eneo-module-bff`: the Eneo SSO handoff, server-side sessions and renewal, a deny-by-default proxy, guarded transport helpers, bounded uploads and signed-file streams, shared heavy-I/O admission, branding and static UI serving.
- Deployment accent settings validate contrast against the Eneo theme and derive a dark-mode colour when omitted. The template loads their same-origin stylesheet from the BFF before themed content appears; no custom theme or inline script is needed.
- The built UI is served fast: its hashed files under `/assets` are kept for a year, the page and the files beside it are asked for again with an ETag (304 while they are the same), and a `.br` or `.gz` the build writes beside a file goes to a browser that accepts it. `HEAD` is answered like `GET`. A JSON answer of Eneo's of 1 KiB or more goes gzipped to a browser that accepts it.
- `GET /health` says which build runs: the commit, the build time and the repository the image was built from, and the release the deployment names, each `null` when not known.
- `@eneo-ai/module-kit`: the pinned Astryx theme, colour mode, providers, shell, branding, session client, and `VersionInfo` with `CopyButton`: which build runs, from `/api/healthz`, with copyable support details. `base.css` lets a menu longer than Astryx's 300 px cap take the window below the top bar, so the account menu's last row is not hidden behind a scroll. Its Astryx integration adds two reference page templates, a documentation topic and generated agent guidance.
- The top bar has the brand mark's height from the first frame, so a page does not move down when the organisation arrives.
- `BrandingProvider` asks for the organisation when the first `Brand` shows. A page without a lockup, such as the login window that closes itself, asks nothing and leaves no cut-off read.
- The top bar's brand link and the slider's thumb have the design system's focus ring in every engine; Safari's own ring on the link was under 3:1.
- Shared form fields have one focus frame along their rounded edge, supporting text follows a 14 px default, and error text and control edges meet AA contrast. Dialog headings receive initial focus without a control frame.
- `@eneo-ai/module-kit` has the building blocks of a module's pages, router-free: `RouteEffects` (each page's title, announced, the focus on its heading, the scroll on Back), `NotFoundPage` and `ErrorPage`, `LoadingShell`, `SlowWait`, `lazyLoader` with `LoadFailure`, `OfflineBanner` and `useConnection` (no network, or a module that does not answer), `errorAdvice` (what a failed request says, in Swedish), `createDrafts` (typed work kept per person in the tab), `useLeaveQuestion` (asks before a page that holds work is left) and `uploadWithProgress`. `ModuleProviders` sends a link to one of the module's own pages through the router and any other as a plain anchor. The colour mode is set before the first paint (`color-mode.js`) and switches without transitions. The theme balances headings, shows where a wide table scrolls, and gives the switch's off track a visible edge and a text area a 44 px touch height; with reduced motion spinners and progress bars stand still.
- The module template supplies a guarded backend, Swedish UI, stub Eneo, browser and accessibility checks, one-process image, local development and CI configuration.
- The template runs on React Router's data router: a title per route, a page's code fetched when it is first entered, a not-found page for an unknown address and an error page for a page that fails. The flow list reads every page Eneo says follows; its note is kept per person in the tab, and leaving asks first while the browser could not keep it.
- The template's browser tests run in two workers: each test has a scope of its own in the stub Eneo, so one that ends its login ends no other's. CI runs them in shards. Its build writes a `.br` and a `.gz` beside each asset; `npm test` runs its unit tests and guards (no network call outside `src/session.ts`, none in a unit test); `npm run test:prod` checks what the backend sends with the built UI: headers, caching, compression, routes, page weight, a release that took away an open page's files.
- The template's CI builds its image once, runs it as the compose file does and publishes it as `sha-<commit>` after every job passed; a tag `vX.Y.Z` gives that image its version without rebuilding it and creates the GitHub Release. Its production compose file runs the image read-only, without capabilities, chosen by `MODULE_VERSION`, and a Traefik overlay adds HTTPS, HSTS and a read timeout for uploads. The account menu's Version opens the build's details in a dialog.

Both packages use AGPL-3.0-only. Their 0.x APIs remain provisional until a second module has used them. 0.1.0 is released as assets of the GitHub release `v0.1.0`, built by CI from the tagged commit: the UI package's tarball, the BFF's wheel and sdist, and `SHA256SUMS`. Publishing to npm and PyPI is pending. Install them by their address: [the BFF](https://github.com/eneo-ai/eneo-module-kit/blob/v0.1.0/docs/guides/build-a-module.md#1-install-the-package), with the wheel's hash, and [the UI package](https://github.com/eneo-ai/eneo-module-kit/blob/v0.1.0/docs/guides/ui-package.md#install).
